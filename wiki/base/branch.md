# Инструкция по веткам в git (проект на Godot)

## Структура веток

| Ветка | Назначение |
|---|---|
| `main` | Стабильная, всегда играбельная версия. Сюда попадает только проверенный код. |
| `dev` | Рабочая ветка. Сюда мержится всё текущее из `fix/*` и `feature/*`. Периодически мержится в `main`, когда всё стабильно. |
| `fix/*` | Короткоживущие ветки для исправления багов. Пример: `fix/collision-bug`. |
| `feature/*` | Короткоживущие ветки для новых фич. Пример: `feature/inventory-system`. |
| `other` | Всё, что связано с **wiki** и папкой **docs** (документация, заметки, вспомогательные материалы). Не относится к игровому коду. |

Ветки `fix/*` и `feature/*` — это шаблон, а не одна ветка. Для каждого бага/фичи создаётся своя ветка с понятным названием после слэша.

---

## Как создать ветку

```bash
# Переключиться на актуальную dev и обновить её
git checkout dev
git pull

# Создать новую ветку и сразу переключиться на неё
git checkout -b fix/collision-bug
# или
git checkout -b feature/inventory-system
```

## Как работать в ветке

```bash
# После правок кода:
git add .
git commit -m "Fixed collision detection for player"

# Отправить ветку на GitHub (первый раз с флагом -u):
git push -u origin fix/collision-bug
# в следующие разы просто:
git push
```

## Как влить изменения обратно

**Важно: мерж не делаем в одиночку.** Прежде чем нажать "Merge", нужно написать в чат команды, что ветка готова к слиянию, и дождаться, пока все посмотрят/согласятся. Только после этого мержим.

1. Закончил работу в ветке → написал в чат: например, "готов `fix/collision-bug`, можно мержить в `dev`?".
2. Дождаться, пока остальные посмотрят изменения (на GitHub или локально) и скажут ОК.
3. Зайти на GitHub → появится кнопка **Compare & pull request**.
4. Указать, куда мержить: `fix/*` и `feature/*` → в **`dev`**; `other` → тоже отдельно, не смешивать с игровым кодом.
5. Написать описание, что сделано.
6. Смержить (**Merge pull request**).
7. Удалить ветку (кнопка **Delete branch** на GitHub, либо локально `git branch -d fix/collision-bug`).

Когда `dev` накопила достаточно стабильных изменений — отдельным PR мержим `dev` → `main`. Мерж в `main` **обязательно** согласовываем в чате со всей командой перед тем, как нажать кнопку — это самая важная ветка.

## Ветка `other` (wiki и docs)

Всё, что кладётся в папку `docs/` или относится к wiki проекта, ведётся в отдельной ветке `other`, не смешиваясь с `main`/`dev`. Логика та же:

```bash
git checkout other
git pull
# правки в docs/ или wiki
git add .
git commit -m "Updated setup instructions in docs"
git push
```

При необходимости `other` можно мержить в `main` отдельным PR, когда документация обновлена.

## Про защиту веток (Branch protection)

На бесплатном GitHub-плане техническая защита веток (и Rulesets, и классические Branch protection rules) **недоступна на приватных репозиториях** — работает только на публичных, либо начиная с платного плана (GitHub Pro/Team).

Поэтому пока используем **договорённость внутри команды** вместо технической защиты:

- Никто не пушит force push и не удаляет ветки `main`/`dev` без согласования.
- Никто не мержит в одиночку — см. правило выше: сначала пишем в чат, ждём, пока все посмотрят, потом жмём "Merge".
- Если позже перейдёте на платный план или сделаете репозиторий публичным — защиту `main` и `dev` стоит настроить технически (Settings → Branches → Add branch protection rule).
